# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Phoenix 1.8 LiveView app packaged as a Docker container and served on Cloudflare Containers, fronted by a Worker + Durable Object. `README.md` is the short entry point; the detail lives in `docs/` — `architecture.md` (the gateway pattern and its rules), `setup.md`, `deploy.md`, `authentication.md`, `realtime.md`, and `troubleshooting.md`. Read `docs/troubleshooting.md` before debugging anything here: it covers reading the Worker's logs and inspecting D1 and the mail queue, and logs the defects this setup has already produced. `app/AGENTS.md` holds the Phoenix/Elixir/LiveView coding rules and applies to everything under `app/` — read it before touching Elixir or HEEx.

## Architecture

```
Client (HTTPS) → Worker (src/index.ts) → ElixirContainer (Durable Object) → container, Phoenix on :4000
                                                                                  ↓ http://d1.internal
                                                              D1Gateway (WorkerEntrypoint) → D1 binding `DB`

dev: no Worker — App.D1 talks to App.D1.LocalGateway on 127.0.0.1:4100 (SQLite file)
```

Seven pieces that only make sense together:

1. **`src/index.ts` — Worker + `ElixirContainer` Durable Object.** The default fetch routes *every* request to a single DO instance (`getByName("singleton")`). The DO starts the container on first request, polls `GET /health` until 200 (up to ~30s), sets a 10-minute inactivity timeout, then proxies HTTP and WebSocket traffic verbatim to port 4000, injecting `x-forwarded-proto: https`. Container env (`SECRET_KEY_BASE`, `PHX_HOST`, `PORT`) is passed at `container.start()` from Worker secrets — the image carries no config.

   Instance type (`basic`) is passed to `container.start()` rather than set as `instance_type` in `wrangler.toml`: `scheduling_policy = "durable_object"` means the DO chooses image and size on every start, and omitting it would get `lite` (256 MiB). A proxy that throws, or a container that never becomes ready, answers 503 with `retry-after` and logs the exception, so no throw reaches a user as Cloudflare error 1101.

   **A deploy does not replace a running container by itself** — `startAndWait()` skips `start()` while one is running, and every request renews the inactivity deadline, so an old image can keep serving indefinitely while the deploy reports success. `rollStaleContainer()` closes that: the DO records the image it started in its storage and stops the container when a deploy changes it. Don't remove it, and don't switch the comparison to `container.inspect()` — comparing against what we started is what keeps an unrecorded container stale and a string-format difference from becoming a restart loop.

2. **`MailGateway` (also `src/index.ts`) — the email path.** Same shape as the D1 gateway below: `interceptOutboundHttp("mail.internal", ...)`, and `App.Mailer.Gateway` (a Swoosh adapter) POSTs to it. Exists so no Email Sending token — which is account-wide — ever lands in the container image. The gateway pins the sender from `MAIL_FROM`, ignores the caller's `from`, allows one recipient, and refuses cc/bcc/attachments/headers; `App.Mailer.Gateway` refuses the same set rather than dropping it. `MAIL_FROM` gates the whole path: unset, and the intercept is never registered, the mailer stays `Swoosh.Adapters.Local`, and `App.Accounts.email_delivery_available?/0` keeps the mail-dependent flows hidden. Changing either half means changing the other, as with D1.

3. **`D1Gateway` (also `src/index.ts`) — the database path.** Before starting the container, the DO registers `container.interceptOutboundHttp("d1.internal", ctx.exports.D1Gateway(...))`. Phoenix then talks to D1 by making plain HTTP calls to `http://d1.internal/tasks...` (`App.D1`, using `Req`). Nothing is exposed publicly and no DB credentials exist in the image. This requires `compatibility_flags = ["enable_ctx_exports"]` in `wrangler.toml`, and the gateway is only registered when `env.DB` exists.

   **Adding a table/endpoint means editing four places in lockstep**: a migration (authored as an Ecto migration in `app/priv/migration_repo/migrations/`, then exported to `cloudflare/migrations/` with `mix d1.gen_migrations` — see point 4), a route + parameterized query in `D1Gateway`, a client function in `app/lib/app/d1.ex`, and the same route in `App.D1.LocalGateway.Router` (the dev/test stand-in — drift between the two makes local runs lie about production). Keep all SQL parameterized (`?1`-style binds). `tasks`, `messages`, `rooms`, `room_memberships`, `users` and `users_tokens` are all wired this way — copy any of them.

   **`tasks` is owned data, and ownership is enforced in SQL.** Every task route takes a `user_id` (query string, or the body on `POST`) and binds it alongside the id in every statement, so another user's task is a 404 rather than a leak — that filter is the only thing standing between two accounts, so don't drop it from a statement when adding one. `App.Tasks` takes an `App.Accounts.Scope` as its first argument and matches it, so a scope with no user raises rather than quietly reaching for someone else's rows, and `/tasks` lives in the `:require_authenticated_user` live session. Migration `0004` added `tasks.user_id` nullable on purpose (additive, so the old version keeps serving during a deploy); rows created before it have a NULL owner and are therefore invisible.

   **Chat rooms are owned the same way, with two deliberate twists** (migration `0006`, the room routes in `D1Gateway`, `App.Chat`). First: **a room with no `rooms` row is a *link* room, open to any signed-in account holding the slug** — the behavior every room had before rooms became rows — so `lobby`, the smoke test's room and rooms opened by slug need no row at all, and there was no backfill. A row only exists once a user *creates* a room (slugs are always generated by `App.Chat.new_room/0`, never typed in, so the default room can never be claimed); its `visibility` (`link`/`private`) plus `room_memberships` decide who may read and write, checked in SQL on every message read and write, and a row that denies the viewer answers **403, never an empty transcript** — `App.D1` maps it to `{:error, :forbidden}`. Second: **`App.Chat` passes the viewer to the gateway on a read instead of matching a scope**, so admission stays the gateway's SQL decision rather than being re-derived in Elixir; writes and room management (create/rename/share/revoke/delete) do match a scope with a user. Two consequences to preserve: `:ephemeral` persistence happens only on `:gateway_unreachable` — a gateway that answered and refused must stay an error with no broadcast, or a revoked member keeps talking — and revocation broadcasts `{:access_revoked, id}` (deletion `{:room_deleted}`) on the chat topic, which is what disconnects live sessions, since authorization is otherwise only checked on entry. Sharing is with existing accounts only (no invitation email; link visibility is the escape hatch), and the sharing UI lives at `/rooms` behind `:require_authenticated_user`.

   `PATCH /users/:id` is the only route that writes more than one statement: it updates the user and optionally deletes their tokens inside a D1 `batch` (one implicit transaction), mirrored locally by `App.D1.LocalGateway.transaction/1`. That batch is what replaces the `Repo.transact/1` the auth generator relied on — don't split it into two requests.

4. **D1 is not an Ecto repo.** `App.Tasks.Task` is an `embedded_schema` used purely for casting/validation; `App.Tasks` applies the changeset with `Changeset.apply_action/2` and persists via `App.D1`. `App.Accounts.User` and `App.Accounts.UserToken` follow the same pattern. `mix ecto.migrate` does **not** apply to D1 data — there is no Ecto adapter for D1 — but migrations are still *authored* with the Ecto migration system: write an Ecto migration in `app/priv/migration_repo/migrations/` (`NNNN_snake_name.exs`, next zero-padded version), run `mix d1.gen_migrations`, and commit both it and the `cloudflare/migrations/NNNN_snake_name.sql` it exports; Wrangler applies the exported file to D1 and `App.D1.LocalGateway` applies it locally. Never edit or regenerate a `.sql` that already shipped (D1 tracks applied migrations by file name); `App.D1.MigrationParityTest` fails the suite if the two expressions of the schema drift. The exporter runs the migrations through `ecto_sqlite3` (dev/test dep) against a scratch SQLite database via `App.MigrationRepo`, which is never supervised. `App.Repo` (Postgres) and `App.Release.migrate` are vestigial — both are no-ops unless `DATABASE_URL` is set (see `App.Application.start/2`, which only supervises `App.Repo` when that env var exists).

5. **`App.D1.LocalGateway` — local persistence without Docker.** Compiled only outside `:prod` (Exqlite is a dev/test dep) and started only when `:d1_local_gateway` is configured, which `config/dev.exs` does alongside pointing `:d1_url` at `http://127.0.0.1:4100`. It serves `D1Gateway`'s HTTP contract from `app/priv/d1_local.sqlite3`, applying `cloudflare/migrations/*.sql` on boot (idempotent, tracked in a `local_migrations` table) — so `mix phx.server` gets real, restart-surviving persistence and the migrations get exercised locally. `App.Application` reaches it through a module attribute (`@local_d1`) so `:prod` never compiles a reference to a module that isn't there. It does **not** cover the `d1.internal` outbound intercept or real D1; that still needs `wrangler dev`.

6. **`App.Accounts` — `mix phx.gen.auth` without a Repo.** Generated with `mix phx.gen.auth Accounts User users --live --hashing-lib bcrypt`, then ported: every `Repo.*` became a gateway call, and the generator's `UserToken.verify_*_query/1` became a fetch by `{context, token}` plus a `*_valid?/1` check, so the validity windows stay in `App.Accounts.UserToken` where the generator put them. `unsafe_validate_unique/3` is a read through the gateway; the unique index on `lower(users.email)` is the real check and its 409 becomes a changeset error. Emails compare case-insensitively via `lower(email)` because D1 has no `citext`; token bytes are stored as lowercase hex; timestamps are `TEXT` in SQLite's `CURRENT_TIMESTAMP` format.

   **Delivery is only configured when `MAIL_FROM` is set** (it switches `App.Mailer` to `App.Mailer.Gateway` in `config/runtime.exs`), and the generated notifier assumed a provider was always there: the Local adapter plus `config :swoosh, local: false` in `config/prod.exs` means delivering exits with `:noproc`. `UserNotifier.delivery_configured?/0` gates every send (`App.Accounts.email_delivery_available?/0` is the context-level name), the magic-link and email-change forms are not rendered while it is false, and no token is written for an email that cannot be sent. Setting `MAIL_FROM` opens both flows with no code change — don't hardcode the guard either way.

   **Registration takes a password and sends no email** (by design — see `docs/authentication.md`), which `mix help phx.gen.auth` warns enables credential pre-stuffing. The prescribed mitigation is load-bearing, not decoration: `login_user_by_magic_link/2` takes the current user and refuses to confirm an unconfirmed, password-holding account unless the requester is already logged in as that user, and `AppWeb.UserLive.Confirmation` mirrors that check in the UI. Don't drop either when wiring the mailer; add a password-reset flow instead, which is what lets a victim recover.

7. **Two socket paths, verified separately, both signed in.** `/chat` (`AppWeb.ChatLive`) runs on LiveView's `/live` socket; `/probe` runs a plain-JS `Phoenix.Channel` client (`assets/js/channel_probe.js`) on `/socket`, mounted with `longpoll: false`. The split is deliberate: `app.js` sets `longPollFallbackMs`, so a broken WebSocket upgrade degrades LiveView to long-polling *silently*. Both pages display the live transport, and `GET /health/sockets` returns the same facts as JSON. Keep `longpoll: false` on `/socket` and keep the transport visible — removing either re-hides the failure mode this demo exists to catch. `scripts/ws-smoke.mjs` (`pnpm ws:smoke <url>`) asserts the handshake, join and broadcast round trip, and runs post-deploy in CI.

   **Chat requires a logged-in account, like `/tasks`.** `/chat` sits in the `live_session :require_authenticated_user` block; `/probe` is a controller route behind the same plug. `/socket` cannot read the session, so the root layout mints a signed token (`AppWeb.UserAuth.user_socket_token/1`) into `<meta name="user-token">`, `channel_probe.js` sends it as a socket param, and `AppWeb.UserSocket.connect/3` verifies it and resolves the account — a bad token is a refused upgrade (silently downgrading to anonymous would present as unexplained denials). `AppWeb.UserSocket.id/1` is `AppWeb.UserAuth.user_socket_topic/1`, and both log-out and the password/email flows broadcast a disconnect there, because the channel socket authenticates outside the session and deleting the session row alone would leave it connected — use the helper on both ends rather than writing the topic out, or they drift and the broadcast reaches nobody. The sender is then taken from `socket.assigns.scope`, never from the client: `App.Chat.create_message/3` matches an `App.Accounts.Scope` and sets `user_id`/`nickname` outside `cast/3`, because a name a client can set is a name it can borrow. Reads stay room-scoped rather than owner-scoped — a room is a shared space whose slug is the capability, and scoping history by sender would also break the cross-socket check this demo exists for.

   **Rooms are owned rows, and authorization is a SQL predicate.** `/chat/:room` and `/probe/:room` take slugs generated by `App.Chat.new_room/0`; a slug with no `rooms` row is an implicit *link* room that any signed-in account may open, which is what every room was before rooms existed, so there is no backfill. A row appears when a user claims the slug, and only then can the room be `private` — the owner plus the accounts in `room_memberships`. The gateway decides that, not the web layer: every message read and write binds the viewer alongside the room, so a denial is a `403` (`{:error, :forbidden}`) rather than an empty transcript. `/rooms` (`AppWeb.RoomLive`) is the management surface. Because authorization is otherwise only checked on join, revoking a member broadcasts `{:access_revoked, user_id}` and deleting a room broadcasts `{:room_deleted}`, which both surfaces handle — without those, a revoked member keeps receiving the room until they reconnect.

   A room name reaches both a channel topic and the database, so it is validated with `App.Chat.valid_room?/1` in `RoomChannel.join/3` and coerced with `room_or_default/1` at the web edge — keep both. Presence is keyed by user id on both surfaces, so they have to agree on what a key means.

   `scripts/ws-smoke.mjs` therefore signs in before connecting, which needs `SMOKE_EMAIL`/`SMOKE_PASSWORD`; the post-deploy step in CI is skipped without them.

   `App.Chat` broadcasts on `"chat:<room>"`, deliberately *not* the `"room:<room>"` channel topic — a channel is already subscribed to its own topic, so broadcasting there delivers every message to `RoomChannel` twice. Chat degrades to in-memory (`:ephemeral`) when the D1 gateway is unreachable so the transport can be tested without a database.

## Commands

The everyday ones are in the [`justfile`](justfile) (`just --list`), whose header explains which of the three local modes to use: `just dev` (native Phoenix with the local D1 gateway — the normal one), `just worker-dev` (`wrangler dev`, the only mode that exercises the gateways), and `just image-run` (the production image, no database). Also `just test`, `just precommit`, `just fmt`, `just reset-db`, `just tail`, `just migrate-local`, `just smoke <url>`. The underlying commands:

Elixir (run from `app/`):

```bash
mix setup                      # deps + assets (ecto.setup needs local Postgres)
mix deps.get && mix assets.setup && mix assets.build   # the Postgres-free equivalent
mix phx.server                 # dev server on :4000, with local D1 persistence on :4100
rm priv/d1_local.sqlite3       # reset the local D1 stand-in database
mix test                       # no Postgres needed: the `test` alias only runs ecto.create/
                               # ecto.migrate when DATABASE_URL is set (see mix.exs)
mix test test/path_test.exs:42 # single test
mix test --failed
mix precommit                  # compile --warnings-as-errors + deps.unlock --unused + format + test
mix format
mix d1.gen_migrations          # export cloudflare/migrations/*.sql from the Ecto migrations
                               # in priv/migration_repo/migrations (see point 4 above)
```

Worker / Cloudflare (run from the repo root; `pnpm` is the package manager):

```bash
pnpm exec wrangler dev                                                  # local Worker (reads .dev.vars)
pnpm exec wrangler deploy                                               # see caveat below
pnpm exec wrangler d1 migrations create phoenix-cf-container-db <name>   # don't: author an Ecto
                                        # migration + mix d1.gen_migrations instead (point 4)
pnpm exec wrangler d1 migrations apply phoenix-cf-container-db --local
pnpm exec wrangler d1 migrations apply phoenix-cf-container-db --remote
pnpm exec wrangler tail                                                 # Worker logs
pnpm ws:smoke https://<host>                                            # WebSocket/channel smoke test
```

**Deploy from CI, not locally, on Apple Silicon.** `wrangler deploy` cross-builds the `linux/amd64` image under QEMU and the BEAM crashes during dependency compilation. Pushing to `main` runs `.github/workflows/deploy.yml` on native AMD64 `ubuntu-latest`. The `ERL_FLAGS="+JMsingle true"` lines in both Dockerfile stages are a workaround for this same QEMU bug — don't remove them.

D1 migrations are applied by CI **before** `wrangler deploy` (`.github/workflows/deploy.yml`), using the `DB` binding so no database name is duplicated there. Code therefore cannot ship ahead of its schema, and a failed migration blocks the deploy. Keep migrations additive anyway — the previous version keeps serving traffic while the new one rolls out. Applying by hand is only for getting schema live ahead of a deploy; the command is idempotent.

## Gotchas

- D1 calls in tests are stubbed with `Req.Test` via `App.D1Stub` (`:d1_req_options` in `config/test.exs`). Channel and LiveView tests must be **non-async** — the stub is resolved in shared mode because the request is made from the channel/LiveView process, not the test process.
- For the auth tests, hand-written stubs would be lying about SQL that has to actually run (unique index, `RETURNING`, the batched update-and-delete), so `App.D1Stub.stub_d1_sqlite!/1` points the stub at `App.D1.LocalGateway.Router` over a throwaway SQLite file built from `cloudflare/migrations` — per-test isolation, the way the Ecto sandbox would give it. Use it (`setup :stub_d1_sqlite!`) for anything touching `App.Accounts` — which now includes the chat pages, since they require a session. `stub_d1_sqlite_without_chat!/1` is the same thing with `/messages` refusing connections, for testing chat's ephemeral mode while the session's user is still readable.
- `App.AccountsFixtures` reads rows back with `App.D1.LocalGateway.query/2` rather than through the gateway's HTTP contract, deliberately: test-only needs (backdating a token, clearing a password hash) must not become gateway routes.
- A `phx-hook` that only pushes events must **not** sit on a `phx-update="ignore"` element; that would block the server from updating the element it reports into (this bit the `/chat` diagnostics card).
- `/health` must stay unauthenticated, fast, and excluded from `force_ssl` (`config/prod.exs`) — the DO's readiness poll depends on it, and the container never becomes ready if it redirects.
- **D1 rejects `undefined` in `bind()`** — it throws rather than treating it as NULL — while `App.D1.LocalGateway` binds `nil` for the same case without complaint. So an absent optional value must go through `bindable()` in `D1Gateway` before it reaches `bind()`. This is the one gateway difference the mirrored HTTP contract cannot catch: `tasks` and `messages` had no nullable columns, so nothing bound an absent value until `users` arrived, and registration 500ed in production with a full green test suite. (`tasks.user_id` and `messages.user_id` are nullable too, but both are required on every route that writes them and so never bound as absent.)
- **The proxy must set `redirect: "manual"`.** `fetch` defaults to following redirects, and following one after a POST means replaying a body that arrived as a stream — which throws, leaving the Worker with no response and Cloudflare serving error 1101 (as HTTP 500). The side effects on the Phoenix side still happen, so it looks like a failure that wasn't one. Nothing before auth could trigger it: every other POST in this app goes over a WebSocket, and all three auth form POSTs answer with a 302. `scripts/ws-smoke.mjs` asserts a form POST redirect survives the proxy.
- **JSON has no `undefined`, so `null` means "absent" on every gateway.** Elixir sends `null` for a field it has no value for; a gateway reader that treats `null` as *invalid* rejects the message. That shipped twice — `bind(undefined)` on the D1 side, and a `null` `reply_to` making `MailGateway` 400 every email the app sent. Use the `readOptional*` helpers for anything optional, and never let a rejection path return without logging: a silent 400 from a gateway is indistinguishable from success, because the Worker invocation still reports `ok`.
- Container disk is ephemeral. Durable state belongs in D1.
- `App.D1.LocalGateway` binds port 4100, so only one dev server runs at a time — a second one fails to boot there, and the error names Bandit rather than the port.
- Assets are Elixir-managed (`esbuild`/`tailwind` Hex packages); there is no Node.js in the Docker build and no `assets/package.json`. Tailwind v4, no `tailwind.config.js`.
- Secrets (`SECRET_KEY_BASE`, `PHX_HOST`, and `MAIL_FROM` when email is wired) are Worker secrets set with `wrangler secret put`, mirrored into `.dev.vars` for local dev. They reach Phoenix at `container.start()`, so **changing one does not take effect until the container restarts** — a secret change publishes a new Worker version but leaves the running container alone, and `rollStaleContainer` only reacts to a changed image.
